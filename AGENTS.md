- Roles live in `public.user_roles` (checked via `has_role`); `profiles.role` is a read-only mirror set only by the `set_account_type` RPC — prevents users from escalating their own role.
- Profiles are created only by the `on_auth_user_created` trigger; the client never inserts profiles — avoids duplicate/racing profile creation.
- All non-public routes sit under `ProtectedRoute`; venue-only routes under `RoleRoute` — one place for access rules.
- Venue access is checked via `venue_members` + `is_venue_member`; verification fields (`verification_status`, `is_verified`) change only through `admin_set_venue_status` — owners can't self-verify.
- Event visibility (drafts, min_age gate, blocks) is enforced in the `events` SELECT policy, not in the UI — direct links obey it too.
- Venue logos and event covers live in the public `post-media` bucket under `<user_id>/venue-logos|event-covers/` — the workspace blocks creating new public buckets.
- Attendance is shown only via `event_visible_attendees` (opt-in, max 8) — no full attendee lists.
- `posts.on_site_verified` is set only by `verify_post_location` (≤ 200 m, server-side); hidden posts use `deleted_at` and are excluded by the posts SELECT policy.
- DMs follow the request model via `dm_allowed`: first message is a request, further messages only after acceptance — enforced in the `direct_messages` INSERT policy.
- Push permission is requested only after an explicit ask — `PushPrimer` after the first RSVP, or ringing a profile bell — both via `registerForPush`; every send goes through `_shared/push.ts` `sendPush` (prefs, caps, dedupe).
- Profile bell (`profile_subscriptions`, own rows only via RLS): every new post/story of the account and every published deal of its venue pushes to bell subscribers via the outbox (`bell_recipients_for_post` / `bell_recipients_for_offer`, enforce blocks + visibility). Bell pushes use category `subscription`: no caps, no quiet hours by product decision, and they don't count toward other caps. Venue accounts only notify once their venue is `approved`.
- Onboarding chip choices share a wrapping layout in `StaggeredChips`; keep selection rules in the individual steps so visual fixes cannot change single/multi-select behavior.
- Discover area-search and card-to-pin navigation use the map's privacy-adjusted display coordinates, never raw private-event coordinates — preserves location privacy across both surfaces.
- Event-card crew previews use `EventSocialContext` with `event_visible_attendees` intersected with following IDs and public profiles — never broaden opt-in attendee visibility for social context.
- Discover heat (bubble size + heatmap) comes only from `event_heat` (RSVPs, event/venue posts, nearby counts split into RSVP'd/walk-in) scored in `src/lib/eventHeat.ts` (`HEAT_WEIGHTS`); nearby presence is written only via `ping_event_presence` (foreground, live events only, ≤ 100 m with RSVP / ≤ 50 m without, nearest event only, 30-min expiry) and suppressed below 3 server-side — never use `expected_attendees` or expose individual presence.
- Location consent lives only in `privacy_settings.location_enabled` (default off), changed only via `set_location_enabled` (records `user_consents`, wipes presence when off) through `useLocationConsent`; `ping_event_presence` and `verify_post_location` require it. Asked once after onboarding by `LocationGate`; declined users get in-app reminders only (2nd open within 1 h, max 1×/7 days, stop after 3 dismissals, open tracking stays on-device) — never push for location.
- Deals (`venue_offers`): guests activate only via `claim_deal` (window, 18+ for `category = 'alcohol'` forced by trigger, contingent with row lock, 1× per user, not own venue); `offer_activations` carry a 64-hex `claim_token` (QR) + 6-char `short_code` and are never written by clients. Redemption only via `redeem_deal` by `can_scan_venue` (venue members or `venue_staff`), atomic, every attempt logged in `deal_scans`; foreign codes reveal nothing. Bar staff live in `venue_staff` (scan-only, invited via `create_staff_invite`/`accept_staff_invite`) — never add them to `venue_members`, which grants event editing and posting as the venue.
- Wallet (`my_deal_wallet`, `/deals`) is private to the user and cached on-device for offline QR display; public "Deals" tabs exist only for venue accounts. Scanner (`/scan`) uses getUserMedia + jsQR in the WebView — no native scanner plugin.
- The app tour (`AppTour`) is mounted once in `App` (inside the router), never per page/`AppLayout` — it navigates between tabs and a per-page instance restarted at step 1 on every route change. It starts only on the main tabs, is keyed on the user id, and the DB flag `profiles.app_tour_completed_at` is authoritative (sessionStorage is only a hint). Other first-run prompts wait while `useTourActive()` is true.
- Venue reviews only from proven visits: `review_invitations` are opened server-side by triggers (deal redeemed, `on_site_verified` post, `event_presence` at a venue's event) — a bare RSVP never counts; one per guest/venue/night (06:00–06:00 Europe/Berlin, `nightlife_night`), open 7 days; never for venue accounts, owners, members or `venue_staff` (`can_review_venue`). Writes only via `submit_venue_review` / `skip_venue_review`; points are identical for every rating (+5, +3 text ≥ 30 chars, +5 once per completed night) and go to `profiles.social_cloud_points` + `point_ledger`; `admin_remove_review` takes them back. Public data only via `venue_rating_summary` (averages from 5 reviews, last 6 months weigh double) and `venue_reviews_list`. One bundled digest per person via pg_cron `send_review_digests` (daily 11:00 UTC, one reminder after 3 days).
- Review hooks keep a scoped RPC type contract matching the review migration; never patch generated database types to represent pending migrations.
- Review moderation reuses `reports` (target_type `review`, reasons incl. `fake`/`personal_data`); a bad rating alone is never a reason. 3 distinct pending GUEST reporters (`can_review_venue`) auto-hide only the text (`comment_hidden`), never the stars; venue-side reports only queue for admins. Admins decide via `admin_moderate_review` (remove = `admin_remove_review` incl. points, hide_text, keep = unhide + dismiss). Venues can't delete reviews: owner/members (not `venue_staff`) reply once per review via `reply_to_review` (editable, empty deletes, reviewer notified once with `review_reply`).
